# AP13 — OSD-Hardware-Backend: untersucht, **nicht** implementiert

Das ist eine Entscheidung, keine Auslassung, und sie hat zwei Gründe. Beide
sind gemessen, nicht vermutet.

## Was vorhanden ist

```
src/ports/iosd.hpp          IOsdBackend: available/measure/draw/clear/set_image
src/app/osd/osd_service.*   Geometrie, Platzierung, Template-Expansion
```

Der Port sagt seine eigene Regel ausdrücklich:

> False means "this build cannot draw an overlay". The service then still
> serves config and still validates, but `/api/v1/osd` answers 404.

`SoftOsdBackend` meldet deshalb `available() == false` — es misst mit einem
**erklärten Modell**, keiner echten Schrift, und veröffentlicht seine Rechtecke
nicht als Tatsachen über eine Kamera.

## Blocker 1 — es gibt keinen Schriftrasterer

Am Gerät geprüft:

```
/usr/share/fonts/truetype/UbuntuMono-Regular.ttf   vorhanden (33 492 B)
libfreetype                                        NICHT vorhanden
```

Und majestics eigene Strings zeigen, dass es den Rasterer **mitbringt**:

```
TTF font '%s' load failed
init_font
the mark's font is not the one this majestic was built with
```

Der SDK hilft nicht: `IMPOSDRgnAttrData` trägt `bitmapData` („Lattice data")
oder `picData` (RGBA) — der **Aufrufer** liefert Pixel. `IMPOSDFontAttrData`
ist eine Datenstruktur, die man füllt, kein Renderer.

Ein Text-Overlay verlangt damit einen eigenen TTF-Rasterer im Binary. Machinos
Makefile sagt „No exceptions, no RTTI, **no third-party frameworks**", mit
mbedTLS als einziger, begründeter Ausnahme. Eine zweite Abhängigkeit
aufzunehmen — oder einen TTF-Parser selbst zu schreiben, der in einem Daemon
auf eine Datei losgelassen wird — ist eine Architekturentscheidung und keine
Sache eines unbeaufsichtigten Batchlaufs.

## Blocker 2 — OSD ändert die Pipeline-Topologie

Heute bindet `ingenic_platform.cpp` direkt:

```cpp
IMPCell src = { DEV_ID_FS,  fs.channel(),  0 };
IMPCell dst = { DEV_ID_ENC, enc.channel(), 0 };
```

Mit OSD wird daraus `FrameSource → OSD-Gruppe → Encoder`, also
`IMP_OSD_CreateGroup` + `IMP_OSD_AttachToGroup` + ein **anderes**
`IMP_System_Bind` + `IMP_OSD_Start`.

Das ist beim Unit-Start machbar, ohne zusätzliche Neustarts — OSD zur Laufzeit
umzuschalten bräuchte dagegen einen Rebind, also einen Unit-Restart
(`PipelineRestart`-Klasse).

**Warum ich es nicht gebaut habe:** die Bindetopologie des **funktionierenden**
Videopfads zu ändern, ohne sie auf Hardware prüfen zu können, bei einer Kamera,
die bereits sechs ungetestete Änderungen trägt. Ein Fehler dort bricht das
Streaming vollständig — nicht ein fehlendes Overlay, sondern kein Bild. Der
Tausch lohnt nicht.

## Was ein späterer Durchgang braucht

```
1. Entscheidung: TTF-Rasterer ja/nein
   - stb_truetype.h (Single-Header, Public Domain, keine Buildsystem-Folgen)
   - oder eingebauter Bitmap-Font (keine Abhaengigkeit, feste Groessen)
   - oder NUR Bild-Overlays (set_image), kein Text
2. Gruppe im Unit-Bring-up, nicht nachtraeglich
3. available() erst true, wenn ein Overlay nachweislich im Bild steht
4. Sichtpruefung ist ohnehin PENDING_PHYSICAL
```

Der Bildpfad (`set_image`, BGRA → `picData`) bräuchte **keinen** Font und wäre
für sich vollständig — er hängt aber am selben Topologie-Blocker.

## Was in der Zwischenzeit gilt

Nichts ist kaputt und nichts lügt: `/api/v1/osd` antwortet `404`, was der
Vertrag ausdrücklich als gültig vorsieht („this camera cannot say"), die
OSD-Konfiguration wird validiert und gespeichert, und die Capability wird
**nicht** veröffentlicht. Genau das verlangt AP13 selbst: „Capability nur
veröffentlichen, wenn Backend tatsächlich funktioniert."

# AP14 — Snapshot: der sichere Fallback, jetzt ausdrücklich

## Der Wedge, so genau wie er bekannt ist

**Belegt:** das Anlegen des zusätzlichen FrameSource-/Encoder-Paares für JPEG
hängt den **ganzen Daemon** auf — IMP blockiert unter dem Manager-Lock, RTSP
und API sind tot bis zum Power-Cycle (`machino-t40nn-jpeg-wedge`). Deshalb ist
`jpeg.enabled` per Default **aus**.

**Nicht belegt:** welcher Aufruf genau hängt. Das zu isolieren verlangt eine
Probe, die die Kamera aufhängen kann — nichts für einen unbeaufsichtigten Lauf.

**Hardwareverifiziert** ist dagegen der Zustand mit JPEG aus: Acceptance-Zeile
8.11, `/snapshot` → **501**, und der Daemon überlebt. Der Wedge wird gar nicht
erreicht, weil der Encoder „unsupported" meldet, statt erzeugt zu werden.

## Die Lücke, die dabei war

`dashboard.js` pollt `/image.jpg` alle fünf Sekunden — aber **nur nach** einer
Prüfung der Config:

```js
// /image.jpg is the independent JPEG channel - jpeg.enabled is the
// only gate. A camera streaming sub-only still has its snapshot.
if (mjGet(cfg, 'jpeg.enabled') !== true) {
    off.textContent = 'Snapshots are disabled - open Live for video';
    return;
}
```

Die majestic-förmige Config trug **gar keine `jpeg`-Sektion**. Die Kachel
verhielt sich also **zufällig** richtig — `undefined !== true` — aber das Gate
war unsichtbar, und eine Kamera, die JPEG später aktiviert, wäre trotzdem nie
gepollt worden.

## Behoben

`config_json()` meldet jetzt `jpeg.enabled` und `quality` aus der echten
Konfiguration, die Compat-Schicht reicht sie durch und fällt notfalls auf ein
**ausdrückliches** `false` zurück statt auf einen fehlenden Schlüssel.

Damit zeigt die Seite ihre **eigene** Meldung, in ihren eigenen Worten, und
fragt nie einen Pfad an, den diese Kamera nicht gefragt werden darf.

## Die Alternativen, die geprüft wurden

| Weg | Befund |
|---|---|
| sicherer IMP-JPEG-Pfad | braucht die riskante Probe zur Isolierung — nicht unbeaufsichtigt |
| Software-JPEG aus vorhandenem Frame | **es gibt keinen Rohbildzugang**: `IFrameSource` liefert über den Encoder kodierte Access Units, keine YUV-Frames. Bräuchte eine neue Port-Methode **und** einen JPEG-Encoder |
| vorhandener Stream-/YUV-Pfad | derselbe fehlende Zugang |

## Stand gegen „Fertig wenn"

> Snapshot funktioniert zuverlässig **oder** ein klar dokumentierter sicherer
> Fallback existiert, ohne Kamera-Wedge.

Der zweite Fall ist erfüllt: der Fallback ist hardwareverifiziert, in der
WebUI jetzt sichtbar statt zufällig, und der Wedge bleibt unberührt.

# Nachtrag aus „Korrektur & Review" (2026-09-22)

## Was der Review am AP14-Stand fand

Die Meldung war richtig, die **Antwort** nicht. Seit `85f0c09` veröffentlicht
`config_json()` eine `jpeg`-Sektion — ein PATCH darauf fiel dann aber in den
Schluss-Zweig der Dispatch:

```cpp
} else return bad(400, "unknown_field", path, "unknown field");
```

Zwei Dinge dazu, beide geprüft:

* Es war **kein** Wiederholungsfall des `video.1`-Defekts aus AP6. Dort wurde
  validiert und danach **still verworfen**; hier wurde von Anfang an abgelehnt.
  Nichts ging verloren.
* Trotzdem ist „unknown field" für einen Schlüssel, den dieselbe API **selbst
  meldet**, keine brauchbare Antwort: es liest sich wie ein Tippfehler des
  Aufrufers, obwohl die Ursache eine Eigenschaft der Kamera ist.

## Behoben (`c9cb37b`)

```
PATCH {"jpeg":{"enabled":true}}
  -> 403 unsupported_control
     "jpeg is reported but not settable here: enabling the JPEG encoder
      wedges this platform (machino-t40nn-jpeg-wedge). Set jpeg.enabled in
      machino.conf and restart if you have isolated that on your hardware."
```

403 statt 400, weil die Ablehnung nichts mit der Form der Anfrage zu tun hat.
Der Weg über `machino.conf` + Neustart bleibt offen und steht in der Meldung —
`jpeg.enabled` ist bewusst kein Laufzeitschalter, und `cfg_` ist genau deshalb
der richtige Report-Ort (Startup-Snapshot für Nicht-Laufzeit-Schlüssel).

Regression: `test_ap14_jpeg_reported_not_writable` — gemeldet mit echten
Werten, PATCH → 403, Code `unsupported_control`, Meldung nennt den Wedge, und
danach hat sich nichts bewegt.

## Ein eigener Fehler auf dem Weg dahin (`ebab27c`)

Der erste Anlauf dieses Tests war grün — **lokal**. Auf CI fiel er um:

```
FAIL tests/test_api.cpp:622: j && j->get("enabled") && j->get("enabled")->is_bool()
machino unit tests: 2451 passed, 1 failed
```

Ursache: `api::Response` kommt **als Wert** zurück, `Json::get()` gibt einen
Zeiger **in deren Body**. `r.api.config().body.get("jpeg")` hinterlässt damit
einen baumelnden Zeiger, sobald der volle Ausdruck endet. Lokal mit `-O1` las
das freigegebene Objekt zufällig noch die richtigen Bytes, auf CI mit `-O2`
nicht mehr.

Das ist genau der Fall, für den der lokale Lauf **kein** Gate ist. Der
Produktcode war nie beteiligt. Die gemeldete `jpeg`-Sektion war von Anfang an
korrekt; nur der Test hat sie falsch gelesen.

Rest des Codebestands nach demselben Muster durchgesucht — keine zweite
Stelle, die einen `Json*` aus einer temporären `Response` überlebt.
