# Review of AP9–AP11 and the follow-ups

A read of everything written in this batch, looking for defects rather than for
confirmation. Eight findings, all fixed in the same commit. Host tests
1872 → 1889/0; nothing was deployed and no hardware was touched.

The code reviewed is what no one else has read: AP9 (OSD), AP10 (setup/claim),
AP11 (ONVIF, WS-Discovery, HTTP Digest) and the RTSP claim gating. The earlier
packages have been through the user's reviewer.

## Findings

### 1. The ONVIF digest nonce was an offline password oracle — *serious*

`make_nonce()` computed `SHA1("<ts>:Machino:<onvif.password>")`, and
`challenge()` hands that value to **any unauthenticated caller** who triggers a
401. The timestamp is in the clear, so anyone on the network could collect
`sha1(known-prefix ‖ password)` and brute-force `onvif.password` offline at
single-iteration SHA-1 speed. A camera that had Digest enabled was giving away
the material to crack its own password.

**Fixed:** the nonce is keyed with a **process secret** read from
`/dev/urandom` at start-up, never with the password. No entropy ⇒ no secret ⇒
Digest is neither offered in the challenge nor accepted (fail closed), and the
daemon says so in the log. Pinned by a test that asserts the nonce is *unchanged*
when the password changes and *different* when the secret changes.

### 2. Unauthenticated peers could pin 16 MiB of RAM — *serious*

The OSD logo upload needs a raised HTTP body cap, and that raise is applied
from the request line — which happens **before** the session gate. So any
unauthenticated peer could open `max_clients` (16) connections, each slowly
feeding a `POST /api/v1/osd/image` body, and hold `16 × 1 MiB` on a camera with
roughly 21 MB available.

**Fixed:** `MAX_IMAGE_DIM` 512 → **256** (256 KiB per upload, ~4 MiB worst
case). I had picked 512 because "512×512 BGRA is exactly 1 MiB", which is a
tidy number and not a justification. 256×256 is still 13 % of a 1080p frame's
width.

### 3. Credential comparisons were not constant-time

Four of them: WSSE PasswordText, WSSE PasswordDigest, HTTP Basic and HTTP
Digest all used `std::string::operator==`, which stops at the first differing
byte.

**Fixed:** `secure_equals()` in `soap.cpp`, used at all four sites. Length may
short-circuit — it is visible in the message anyway — the content may not.
Impractical to exploit over a network, but there was no reason to leave it.

### 4. A comment could truncate a credential

`element_text()` skipped comments when finding the *opening* tag but not when
finding the *closing* one, so `<Password>ab<!-- </Password> -->cd</Password>`
yielded `ab`. Same class as the bug already fixed in `soap_action()`, missed in
the other function. This runs on unauthenticated input.

**Fixed and pinned by a test.**

### 5. `atoi()` on attacker-controlled query strings is undefined behaviour

Four call sites in the OSD image route. The service range-checks the result, so
the consequence was bounded, but UB is UB.

**Fixed:** a bounded `query_int()` using `strtol` with `ERANGE` and trailing-
garbage checks.

### 6. The logo store deleted the target before renaming

`store_image()` did `remove(final)` then `rename(tmp, final)`, leaving a window
with no logo at all — and losing the old one outright if the rename then
failed. The comment justified it with "rename() will not replace on every
libc", which is not true of any platform this runs on.

**Fixed:** rename directly; POSIX replaces atomically.

### 7. WS-Discovery was an unbounded UDP reflector

A probe's source address cannot be verified, so every reply is a packet a third
party can be made to receive. The amplification is small (the reply is under
twice the probe) but an unbounded responder is a reflector.

**Fixed:** 20 replies a second. Real discovery sends a handful.

### 8. `hello()`/`bye()` were dead code — and wiring them introduced a race

Both were written and tested but the responder never sent either. Wiring them
up then created a data race: `announce()` and the receive loop both touch
`msg_counter_`.

**Fixed:** Hello is sent *before* the thread exists; Bye *after* the join and
before the socket closes. Ordering rather than a lock — the counter has exactly
one writer at any moment, which is cheaper and easier to verify than making it
atomic.

## Checked and found sound

- No `memcpy`/`strcpy`/`sprintf` anywhere in the new code; every fixed buffer is
  `snprintf` and sized for the compiler's worst case (the CI `-Werror=format-
  truncation` failure earlier made that habit stick).
- Every `substr` has a bound established before the call.
- The image store takes an **index**, never a path, so no request can steer
  where a file lands; a corrupted file on disk is re-validated on read.
- The claim state is read fail-closed everywhere (unreadable `/etc/shadow` ⇒
  "claimed" ⇒ no unauthenticated setup page).
- `SetupGate` refuses a colon or newline in the password rather than escaping
  it, and validates the SSH key *before* the claim.
- `OsdService` takes only its own mutex and never calls the backend while
  holding a lock the media path wants.

## Known, accepted, not fixed here

- **`OsdService::pump()` is never called.** There is no timer because there is
  no backend that can draw; both arrive together with the Ingenic backend.
- **The setup password is not wiped from memory** after use. The process
  handles it in several `std::string`s; scrubbing one of them would be theatre.
- **`probe_matches_us()` matches a Types substring**, so
  `NetworkVideoTransmitterFoo` would match. Harmless — it only decides whether
  to answer a discovery probe.
- **The camera-local trust rule still applies while unclaimed** (recorded in the
  AP10 note as a deviation).
- **None of this has run on hardware.** Everything above is host-tested
  reasoning about code, which is not the same as a camera behaving.

# Second pass

A wider read: my own fixes from the first pass, plus code this batch had not
looked at — `session.cpp`, `rtsp_auth.cpp`, and the digest helpers that AP11
made load-bearing for a **second** consumer. Three findings.

## 9. Session tokens and RTSP nonces came from a Mersenne Twister — *medium*

`SessionGate::new_token()` and `RtspAuth::new_nonce()` both used
`std::mt19937_64` seeded from `std::random_device`. MT is not a CSPRNG: its
entire internal state is recoverable from enough output, after which every past
and future draw is predictable. A session cookie is a bearer credential.

**Exploitability, checked rather than assumed: low.** Tokens are only minted
after a credential check, so an attacker cannot harvest them. And the RTSP
generator is `thread_local` while RTSP runs **a thread per connection**, so an
attacker collecting 401 challenges gets one or two draws per generator instance
— nowhere near the hundreds needed to recover MT state.

But that is a property of *today's call sites and connection model*, not of the
generator. Add a guest session, or move RTSP to a thread pool, and it becomes
one. Graded medium and fixed rather than argued away.

**Fixed:** new `core/random.{hpp,cpp}` — `/dev/urandom` on POSIX,
`BCryptGenRandom` on the host build (bcrypt is already linked for mbedTLS, so
the host tests exercise the real path rather than a stub). **There is no weak
fallback**: failure is reported and callers fail closed. This also absorbed the
third answer to the same question, the ad-hoc `/dev/urandom` read `main` was
doing for the ONVIF nonce secret.

## 10. An empty token would have been issued as a session

A consequence of the change above, found while making it. With no randomness
`new_token()` returns `""`, and `login()` would have stored `tokens_[""]` and
sent `Set-Cookie: session=`. Only `authed()`'s empty-token check stood between
an absent Cookie header and a valid session — one guard doing load-bearing work
by accident.

**Fixed:** `login()` answers **500**, `mint()` returns `""`, and no empty token
is ever stored.

## 11. The AP9 note still documented the old 1 MiB limit

Stale documentation created by my own first-pass fix. Corrected, with the
reason for the smaller number recorded next to the number.

## Checked in this pass and found sound

- `RtspAuth` already compares digests with a constant-time `same()`. My concern
  about the newly shared code was unfounded there.
- `auth_param()` rejects a key found inside a quoted value (the boundary test),
  so `cnonce="response=evil"` cannot shadow the real `response`, and `nonce=`
  does not match inside `cnonce=`.
- `SessionGate::authed_basic` refuses any account but root, like the form login.
- `form_value` / `cookie_value` only match at parameter boundaries.
- ONVIF Digest with `qop=auth-int` fails closed: the body is not hashed into
  HA2, so the two sides cannot agree.

## Still knowingly unfixed

- Session **token lookup** is a hash-map compare, not constant-time. Hashing
  dominates and the token is 128 bits; the complexity is not worth it.
- Removing MT does not change anything an attacker could previously do. It is
  hygiene, not an incident, and is graded that way above.

Host tests after both passes: **1934/0** (1872 before the review).

# Third pass

The attack surface that had never been read in this batch: the HTTP request
parser, the WebSocket framer, the JSON limits, the `logread` child, and the log
sink. Three findings, one of them a live concurrency bug.

## 12. The log sink was not thread-safe — *medium*

`log_file_write()` is called from **every thread**: the HTTP poll loop, one
thread per RTSP client, the pipeline, and now the WS-Discovery responder — four
translation units, 75 call sites.

stdio locks a `FILE*` internally, so concurrent `fputs` was fine on its own.
But `rotate()` **closes that `FILE*`** and opens another, and a thread already
inside `fputs` on the old one is then writing through a freed handle. The byte
counter was a plain read-modify-write across the same threads.

The window is the rotation boundary — every 256 KiB of log — so on a busy
camera this was a matter of time, not of luck.

**Fixed:** one mutex over the whole sink. Logging is per event, not per frame,
so the cost is nothing next to the `fflush` that was already there.

## 13. The `logread` child was never reaped

`logs_stop()` sent `SIGTERM` and then called `waitpid(..., WNOHANG)`
immediately, which essentially always returns 0 because the child has not died
yet — and then cleared the pid. The comment claimed it was "reaped again below
if it lingers"; there was no such code. Every open/close of the Logs page left
a zombie.

**Fixed:** unreaped pids go on a pending list and are collected from the poll
loop. A list rather than a single pid, because the next subscriber can start a
new child before the old one has died, and overwriting the pid would have made
it unreapable.

## 14. Ambiguous request framing was resolved instead of refused

`parse_request` took the **first** `Content-Length` when several were present,
and `strtoull` accepted a leading sign, so `Content-Length: -1` wrapped to a
huge value and merely tripped the size check.

Request smuggling was **not** reachable: `forward_request` drops every incoming
`Content-Length` and emits one computed from the body actually parsed, and the
relay is HTTP/1.0 with `Connection: close`, so there is a fresh upstream
connection per request and no cross-request desync. `Transfer-Encoding` in any
form was already rejected outright.

**Fixed anyway:** more than one `Content-Length` is refused (RFC 7230 §3.3.3),
and the value must be digits only. An ambiguous request should not be answered.

## A finding I withdrew

I first reported that accepted client sockets were not `CLOEXEC`, which would
have meant the `logread` child inheriting every live connection. **That was
wrong** — my grep pattern silently matched nothing. Both servers use
`accept4(..., SOCK_CLOEXEC | SOCK_NONBLOCK)` and every listening and UDP socket
is `SOCK_CLOEXEC`. Recorded because a review that only lists confirmed hits
hides how often the first guess is wrong.

## Checked in this pass and found sound

- `parse_frame` bounds the 64-bit WebSocket length against `max_payload`
  *before* reserving, requires the client mask, and refuses fragments and RSV
  bits.
- `JsonLimits` caps nesting at 16, so no depth-based stack exhaustion; the
  raised signalling limits widen strings and total bytes but leave depth alone.
- The request head stays capped at 8 KiB regardless of the raised body cap, so
  the OSD/ONVIF allowance really only affects the body.
- `forward_request` drops hop-by-hop headers and sets `Host` itself.

## Noted, not fixed

- `logs_start()` falls back to `execlp("logread", ...)` after the absolute
  `/sbin/logread` fails, so a `$PATH` lookup runs as root. The daemon's `PATH`
  comes from init and is not attacker-influenced, and the absolute path is
  tried first — but the fallback earns nothing and could go.
- `log_file_open("", 0)` still consults `MACHINO_LOGFILE`, so that test asserts
  "writes nothing" only in an environment where the variable is unset.

Host tests after three passes: **1942/0**.
