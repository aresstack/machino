# Review of AP9–AP11 and the follow-ups

A read of everything written in this batch, looking for defects rather than for
confirmation. Eight findings, all fixed in the same commit. Host tests
1872 → 1889/0; nothing was deployed and no hardware was touched.

The code reviewed is what no one else has read: AP9 (OSD), AP10 (setup/claim),
AP11 (ONVIF, WS-Discovery, HTTP Digest) and the RTSP claim gating. The earlier
packages have been through the user's reviewer.

## Findings

### 1. The ONVIF digest nonce was an offline password oracle — *serious*

`make_nonce()` computed `SHA1("<ts>:Machino:<onvif.password>")`, and
`challenge()` hands that value to **any unauthenticated caller** who triggers a
401. The timestamp is in the clear, so anyone on the network could collect
`sha1(known-prefix ‖ password)` and brute-force `onvif.password` offline at
single-iteration SHA-1 speed. A camera that had Digest enabled was giving away
the material to crack its own password.

**Fixed:** the nonce is keyed with a **process secret** read from
`/dev/urandom` at start-up, never with the password. No entropy ⇒ no secret ⇒
Digest is neither offered in the challenge nor accepted (fail closed), and the
daemon says so in the log. Pinned by a test that asserts the nonce is *unchanged*
when the password changes and *different* when the secret changes.

### 2. Unauthenticated peers could pin 16 MiB of RAM — *serious*

The OSD logo upload needs a raised HTTP body cap, and that raise is applied
from the request line — which happens **before** the session gate. So any
unauthenticated peer could open `max_clients` (16) connections, each slowly
feeding a `POST /api/v1/osd/image` body, and hold `16 × 1 MiB` on a camera with
roughly 21 MB available.

**Fixed:** `MAX_IMAGE_DIM` 512 → **256** (256 KiB per upload, ~4 MiB worst
case). I had picked 512 because "512×512 BGRA is exactly 1 MiB", which is a
tidy number and not a justification. 256×256 is still 13 % of a 1080p frame's
width.

### 3. Credential comparisons were not constant-time

Four of them: WSSE PasswordText, WSSE PasswordDigest, HTTP Basic and HTTP
Digest all used `std::string::operator==`, which stops at the first differing
byte.

**Fixed:** `secure_equals()` in `soap.cpp`, used at all four sites. Length may
short-circuit — it is visible in the message anyway — the content may not.
Impractical to exploit over a network, but there was no reason to leave it.

### 4. A comment could truncate a credential

`element_text()` skipped comments when finding the *opening* tag but not when
finding the *closing* one, so `<Password>ab<!-- </Password> -->cd</Password>`
yielded `ab`. Same class as the bug already fixed in `soap_action()`, missed in
the other function. This runs on unauthenticated input.

**Fixed and pinned by a test.**

### 5. `atoi()` on attacker-controlled query strings is undefined behaviour

Four call sites in the OSD image route. The service range-checks the result, so
the consequence was bounded, but UB is UB.

**Fixed:** a bounded `query_int()` using `strtol` with `ERANGE` and trailing-
garbage checks.

### 6. The logo store deleted the target before renaming

`store_image()` did `remove(final)` then `rename(tmp, final)`, leaving a window
with no logo at all — and losing the old one outright if the rename then
failed. The comment justified it with "rename() will not replace on every
libc", which is not true of any platform this runs on.

**Fixed:** rename directly; POSIX replaces atomically.

### 7. WS-Discovery was an unbounded UDP reflector

A probe's source address cannot be verified, so every reply is a packet a third
party can be made to receive. The amplification is small (the reply is under
twice the probe) but an unbounded responder is a reflector.

**Fixed:** 20 replies a second. Real discovery sends a handful.

### 8. `hello()`/`bye()` were dead code — and wiring them introduced a race

Both were written and tested but the responder never sent either. Wiring them
up then created a data race: `announce()` and the receive loop both touch
`msg_counter_`.

**Fixed:** Hello is sent *before* the thread exists; Bye *after* the join and
before the socket closes. Ordering rather than a lock — the counter has exactly
one writer at any moment, which is cheaper and easier to verify than making it
atomic.

## Checked and found sound

- No `memcpy`/`strcpy`/`sprintf` anywhere in the new code; every fixed buffer is
  `snprintf` and sized for the compiler's worst case (the CI `-Werror=format-
  truncation` failure earlier made that habit stick).
- Every `substr` has a bound established before the call.
- The image store takes an **index**, never a path, so no request can steer
  where a file lands; a corrupted file on disk is re-validated on read.
- The claim state is read fail-closed everywhere (unreadable `/etc/shadow` ⇒
  "claimed" ⇒ no unauthenticated setup page).
- `SetupGate` refuses a colon or newline in the password rather than escaping
  it, and validates the SSH key *before* the claim.
- `OsdService` takes only its own mutex and never calls the backend while
  holding a lock the media path wants.

## Known, accepted, not fixed here

- **`OsdService::pump()` is never called.** There is no timer because there is
  no backend that can draw; both arrive together with the Ingenic backend.
- **The setup password is not wiped from memory** after use. The process
  handles it in several `std::string`s; scrubbing one of them would be theatre.
- **`probe_matches_us()` matches a Types substring**, so
  `NetworkVideoTransmitterFoo` would match. Harmless — it only decides whether
  to answer a discovery probe.
- **The camera-local trust rule still applies while unclaimed** (recorded in the
  AP10 note as a deviation).
- **None of this has run on hardware.** Everything above is host-tested
  reasoning about code, which is not the same as a camera behaving.
